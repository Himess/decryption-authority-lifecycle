# P0.4: the EIP-7851 gap (proof classes: Connector and Mock)

Date: 2026-10-21. Connector runs: VPS, three per tree. Mock runs: M1, three.

## Background (read 2026-10-21; both EIPs are Drafts)

- **EIP-7851, "Code-Controlled EOA Delegation"** (requires EIP-7702).
  - An EIP-7702 account can disable its ECDSA authority permanently. Its code becomes `0xef0101 ‖ delegate` (23 bytes).
  - Execution delegates exactly as with `0xef0100`.
  - The disabled key's transactions are invalid, and its EIP-7702 authorizations are skipped.
  - The EIP notes that contracts which verify ECDSA directly "will not automatically reject signatures from an ECDSA-disabled authority". It defers `ecrecover` to EIP-8151.
- **EIP-8151, "Account Code Restricted ecRecover".**
  - The precompile returns the recovered address only if that account's code is empty, or exactly an EIP-7702 delegation indicator. Otherwise it returns empty output.
  - Solidity-level recovery does not go through the precompile and is not restricted.

Neither EIP changes an off-chain verifier, which recovers signatures in its own code. That is the gap.

## Simulation

No client implements EIP-7851. The test account X gets a real EIP-7702 delegation to E4's ML-DSA-44 ERC-1271 account
(`MLDSA44Account1271`, immutables only), so calls into X run the delegate. The delegation is made two ways:

- locally: a type-4 transaction;
- on the VPS: `anvil_setCode` with `0xef0100 ‖ delegate`. Both anvils used were checked to execute this as a delegation: 1.8.5 on M1, and 1.3.5, the connector harness's (`raw/env/probe_anvil_vps.json`).

The JSON-RPC proxy between every verifier and anvil (`fault_proxy.py --rewrite-file`) answers `eth_getCode(X)` with
`0xef0101 ‖ delegate`. Execution is untouched. Y is the same with a NoErc1271 delegate (no `isValidSignature`). The
reference rows use the same accounts with the rewrite off.

The simulation covers only what a verifier reads. The chain's own EIP-7851 behaviour (refusing the key's
transactions, `SETSELFDELEGATE`) and EIP-8151's precompile are not simulated.

All three runs agree with the connector rows above. Notable results:

## Specification changes (ERC draft)

- **Terminology:**
  - "ECDSA-disabled delegation indicator (EIP-7851)" is added.
  - "Regular code" now names it explicitly.
  - "ECDSA-rooted account" (empty code or a `0xef0100` indicator) does not include it.
- **H2:** regular code, including the ECDSA-disabled indicator, gets ERC-1271 only, with no fallback.
- **Profile Q:**
  - Q4: such an account is migrated, authenticated through ERC-1271.
  - Q5: the delegation cutoff applies only to changes made before the account's ECDSA authority was disabled. A verifier that cannot establish that block applies the cutoff to every change.
  - Q7: such an account counts as migrated.
- **Motivation:** one sentence. Disabling the key on the host chain does not reach off-chain verifiers that recover before reading code.
- **Rationale, "Relation to EIP-7851 and EIP-8151":**
  - Migrate in place (EIP-7851, plus EIP-8151 for on-chain `ecrecover`) or migrate out (a successor and retirement).
  - Off-chain verifiers need H2 either way.
  - With EIP-8151, a delegate that checks the root key through the precompile stops accepting it [I]; one that recovers in Solidity does not.
  - Nothing depends on adoption.
