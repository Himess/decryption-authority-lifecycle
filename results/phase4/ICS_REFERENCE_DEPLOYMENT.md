# Implementation Conformance Statement: the local reference deployment

This is an example ICS (ERC "Implementation Conformance Statement") for the reference deployment that the connector
evidence runs against. It is a worked example, not a production statement. It covers:

- the Level 0 registry on a local anvil chain;
- one kms-worker of the example oracle at main `ed851716c`, unmodified or with Level 1 (Profile H and H7).

Every field of the ERC's ICS table is filled. Where the two worker variants differ, both are given. The file moves to
`assets/` in D1.

| Field | Content |
|---|---|
| Registry | Host chain id 12345: a local anvil, 127.0.0.1. The Level 0 ACL (`ACL v0.8.0` on main) sits behind an ERC1967 proxy and is deployed fresh for each test run with Zama's own flow (`ERC1967Proxy(EmptyUUPSProxyACL)`, then `upgradeToAndCall(ACL, initializeFromEmptyProxy())`). Each run's log has the address |
| Interface ids | Core `0x556d2088` (`retireAccount() ^ isAccountRetired(address)`), checked on every run (`ACL-LEVEL0 supportsInterface(0x556d2088)=true`), and ERC-165 `0x01ffc9a7` |
| Governance | **Upgrade authority:** `_authorizeUpgrade` is `onlyOwner` (`Ownable2Step`), and the owner is one anvil development account. **Timelock delay:** none (0). **Other contracts on the release path:** none deployed; the harness deploys only the ACL, which is the only contract the oracle reads. **Engine address:** the compile-time constant `fhevmExecutorAdd` = `0xe3a9105a3a932253A70F126eb1E3b589C643dD24` (main `host-contracts/addresses/FHEVMHostAddresses.sol:7`); nothing is deployed there on the local chain. This deployment has no production governance, so the third limit applies in full: retirement is as final as one development key |
| Threshold | One kms-worker: n = 1, t = 0. It is not a threshold deployment; restrictive requirements bind because the only node enforces them. Profile H runs on 1 of 1 node in the Level 1 variant and on 0 in the unmodified one. E3 and Profile Q run on 0 nodes |
| **Decision lag** | **L = 0 blocks.** Every view is evaluated at `latest` of the node the worker queries (main `rpc.rs:24-66`, alloy's default `BlockId::Latest`; v0.13.8 `decryption.rs:98-234`). No snapshot is shared across the views of one request. Every attempt evaluates again: retries, restarts, already-sent requests. Reorgs are followed. A retirement binds from the first evaluation after its block (TC14, `P0_2_TC14.md`). The node's own lag behind the network is not measured. A deployment that wants finality-bound retirements would evaluate at `finalized`, with L = the chain's finality depth |
| Stored results | **Unmodified:** a stored successful user decryption result is served again with no new check, for as long as the row exists (main endpoint `decrypt.rs:108-135`; `endpoint.toml`: "Successful results are reused indefinitely"). **Level 1 with H7** (`revalidate_stored_results = true`): before a stored user decryption result is served, the stored payload is dropped and the request goes back to `pending`, so the worker applies V1 again at a fresh decision block. Duplicates attach to that one revalidation. Public decryption results are served as stored, because they are public (R9). Measured in P0.3 (`P0_3_STORED_RESULTS.md`) |
| Transport | **Reply KEM:** ML-KEM-512 in a hybrid with AES-256-GCM, from a code reading of kms `c755e84` (`core/service/src/cryptography/hybrid_ml_kem.rs`, `encryption.rs`; ML-KEM-1024 keys are refused for user decryption). It is not exercised here, because the harness uses a KMS mock. **Transport-key policy:** the key is the `publicKey` that the signed request names. The deployment adds no rule on rotation or reuse. A stored payload stays encrypted to that key for as long as it is kept. Profile H1 (Level 1) caps the key at 4,096 bytes |
| Signatures | **Unmodified:** RFC-012 ordering (`ecrecover` first), with no Profile H caps, budget or attempt limit. **Level 1 (Profile H):** mode `enforce` in the Profile H runs (the shipped default is `off`, H8); `B_exec` = 2,000,000, so the gas limit is `B_exec + 21,000 + 64 × calldata length`; caps of 65,536 bytes for the signature, 4,096 for the public key and 1,024 for extra data; 2 ERC-1271 attempts per request, at least a block apart. Since P0.3 the attempt count is kept in the connector database (`profile_h_erc1271_attempts`), so a restart does not reset it (`shared/user-decryption-signature/src/profile_h.rs:49-63, 135-146`) |
| E3 | Not enabled in this deployment. The branch `lifecycle/level3-connector` (`564d7d1`) implements it in the kms-worker: schemes ML-DSA-44/65/87 (setting `profile_h.kda_schemes`, empty by default) and the K8 mode (setting `profile_h.kda_k8_mode`: `single:<library>` or `agree:<a>,<b>`, default `single:rustcrypto`), with four libraries (`results/phase4/P1_1_E3_CONNECTOR.md`). On this deployment (n = 1, t = 0) K8 could be met only in the agree mode, because any one library would serve t + 1 = 1 node |
| Profile Q | Not enabled (P1.2) |
| Host-state sources | One local node: worker → recording proxy → anvil. All nodes (1 of 1) use it. There is no light client and no second provider, so O3 is not met |
| Succession | The Level 0 registry does not implement E1, so there is no delay D. E1 runs on the Level 2 ACL (TC17) |
