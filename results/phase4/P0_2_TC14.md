## L per line, from code and from the wire

- **main.**
  - Every ACL view goes through `HostRpcClient` (`kms-connector/crates/kms-worker/src/core/event_processor/rpc.rs:24-66`) as `.call()` with no `.block(...)`.
  - alloy-contract 2.2.0 defaults the block to `BlockId::default()` (`call.rs:369, 379`) and sends it (`call.rs:546`). `BlockId::default()` is `BlockNumberOrTag::Latest` (alloy-eips 2.2.0 `eip1898.rs:516-519`).
  - The ERC-1271 call (`shared/user-decryption-signature/src/lib.rs:134-139`) sets no block either, so the node's default (`latest`) applies.
- **v0.13.8.**
  - The calls are at `decryption.rs:98-102` (`isAllowedForDecryption`), `:200-209` (`isHandleDelegatedForUserDecryption`) and `:229-234` (`isAllowed` for user and contract). None sets a block.
- **Wire.**
  - Every `eth_call` the proxy recorded in the TC14 runs carried the block parameter `latest`: 45 per main run, 28 per v0.13.8 run.
  - With `--heads`, the proxy also recorded the node's head after each answer. That head is the block "latest" referred to (anvil mines only on transactions).
- **No shared snapshot.**
  - The views of one request run concurrently (`tokio::try_join!`), each at its own `latest`.
  - The worker pins `finalized` only for KMS-context reads: `context.rs:140, 164` and `protocol_config.rs:111` on main.

So L = 0 with respect to the node the worker queries. A deployment adds that node's own lag behind the network,
which is not measured here.

## The four tests

| Case | What happens | Main, 3 runs | v0.13.8, 3 runs |
|---|---|---|---|
| **After N** | The subject retires at block N; then a request is picked up | refused after 3 attempts, 0 KMS calls; `isAllowed` evaluated at head N | the same |
| **Race (request before N)** | The request's `isAllowed` calls are evaluated at head N−1; the proxy holds their (true) answers 4 s; the subject retires at N meanwhile | **forwarded** (decision block N−1). Retirement mined 34–83 ms after the evaluation; forward seen 4.22–4.34 s after it | **forwarded** (N−1). Retirement 26–68 ms after; forward seen 4.29–4.59 s after |
| **Reorg** | Retired at N, a request is refused; `anvil_rollback(1)` removes block N (`isAccountRetired` = false again); a new request | before: refused; after: **forwarded** | the same |
| **Restart mid-check** | Worker A picks the request, its `isAllowed` answers are held; A stops picking and its in-flight call loses its connection; the row returns to `pending`; the subject retires; worker B picks the row | B **refuses** after re-checking at its own decision block; A made 0 KMS calls | the same |
| **Already sent** | A row marked `already_sent`: a worker sent it to the KMS and stopped. Another worker picks it | subject live: forwarded by polling only (one `GetUserDecryptionResult`, no new `UserDecrypt`); subject retired: **refused**, no poll | the same |

KMS-mock counts: mocktail counts each gRPC call twice. A forward is 4 (UserDecrypt and GetUserDecryptionResult); a
poll alone is 2. The worker log confirms which calls were made.

Sources for the restart behaviour:

- main `processor.rs:64-68` ("Poll-only retry: we still re-run live-state checks").
- v0.13.8 `processor.rs:186-191`: `prepare_request`, which holds the ACL checks, runs before the `already_sent` branch.
- Each attempt is one spawned task (`kms_worker.rs` `spawn_event_processing_tasks`). A failed attempt puts the row back to `pending` (`mark_as_pending`).
- A row left `under_process` by a dead worker is unlocked by the tx-sender's recovery routine: main `operation_recovery.rs:12-23`; v0.13.8 `garbage_collection.rs`.

## What this means

- **Decision block.**
  - The decision is the node's head when the view is evaluated. A retirement included after that block does not stop a request already decided.
  - The window runs from the view evaluation to the KMS request. Here that is 0.2–6 ms on main and 15–53 ms on v0.13.8 (`ACL check passed` to `Sending`, worker log, normal forward). Production adds the RPC latency.
- **Every attempt is a new decision.**
  - A retry, a restarted worker and an already-sent request all evaluate the views again. A retirement between attempts binds the next attempt.
- **Reorgs.**
  - A verifier at `latest` follows the host chain's reorgs. A rolled-back retirement no longer refuses. This is the third limit ("as final as the chain").
  - A deployment that wants retirements to bind only once final can evaluate at `finalized`. That raises L to the chain's finality depth, so retirement binds later. The ICS states the choice.
- **Pre-emptive, not a clawback.**
  - A request decided before N is served (the race case). This is limit 1, measured.

### MultichainACL

On v0.11 the gateway kept a mirror of host-ACL delegations, MultichainACL. Coprocessors propagated the ACL events to
it asynchronously, and the gateway checked it before accepting a delegated decryption request. A replica like this
is what rule V5 addresses: it decides from copied state, so a retirement would bind only once propagated.

It is not on any decryption path at either base:

- No contract, binding or source reference remains in gateway-contracts, kms-connector, relayer or SDK.
- The transaction-sender comment (`coprocessor/fhevm-engine/transaction-sender/src/ops/common.rs:89`) and deployment and CI files are the only mentions.
- The removal dates to v0.12:
  - `charts/coprocessor/values.yaml:123` (v0.13.8 `:76`): "legacy v0.11 txSender only; disable the arg on v0.12+".
  - `test-suite/fhevm/src/compat/compat.ts:387-389`.
  - `ci/preview-env/coprocessor/values-coprocessor-e2e.yaml:282-290`: no `MultichainAcl` contract even at v0.13.0.
- The SDK test comment that describes it: `sdk/js-sdk/test/fheTest/ethers-common/clientDecrypt.delegateDecrypt.tests.ts:146-150`, on both lines.

The references in this section were checked by reading the code at both bases (P0.2). A broader search for them
was drafted by a sub-agent and spot-checked line by line.
