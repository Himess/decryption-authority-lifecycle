# P0.1, TC13: does V1 hold when a view call fails? (proof class: Connector)

Date: 2026-10-21. Machine: VPS (4 vCPU, Ubuntu 24.04, capped scope). Runs: three per line, all passing (rc 0).

## Result

| Line | Runs | V1 cells (authorization views) | Conform | Refusals that reached the KMS mock |
|---|---|---|---|---|
| main `ed851716c` | 3 | 110 | 110 [M] | 0 |
| v0.13.8 `fe3ca89b5` | 3 | 44 | 44 [M] | 0 |

The **unmodified** kms-worker meets V1 on both lines for every failure listed below, on every request path, in all
three runs:

- a JSON-RPC error;
- HTTP 503;
- a dropped connection;
- a delay longer than main's call timeout;
- malformed JSON;
- an empty `0x` result;
- a 31-byte result;
- a revert with or without data;
- an intermittent failure.

A retired subject's request never reached the KMS mock. An allowed subject's request reached it only when a correct
`true` was eventually obtained: under the control case, after a retry under `intermittent`, and late under `delay`
on v0.13.8, which has no call timeout.

The table in `p01/TC13_MATRIX.md` has one row per path, view, subject and fault, generated from the raw runs. The
ERC's Backwards Compatibility claim is now measured. It is stated with one condition (see "What this means for the
ERC").

## How the worker behaves under each failure

The legacy path (gateway transactions) and the RFC-016 on-chain path behave the same. The RFC-016 HTTP path
behaves differently. Both lines show the same per-fault behaviour, except under `delay`.

| Failure injected into the view's `eth_call` | Legacy and RFC-016 on-chain | RFC-016 over HTTP (main) |
|---|---|---|
| none (control), retired subject | refused after 3 attempts; each denial is recoverable, `acl_denied` | refused at once, `acl_denied` |
| JSON-RPC error, HTTP 503, dropped connection, malformed JSON, empty `0x`, 31 bytes, revert with or without data | refused after 3 attempts (transport or decode error, recoverable) | refused at once, `upstream_transient` |
| `delay` 12 s on main (call timeout 10 s) | each attempt times out; refused after 3 attempts | refused at once, `upstream_transient` |
| `delay` 15 s on v0.13.8 (no call timeout) | the worker waits; forwards the late `true`, refuses the late `false` | (no HTTP path at v0.13.8) |
| `intermittent` (first call fails) | allowed: forwarded after one retry; retired: refused after 3 attempts | refused at once, `upstream_transient` (no retry on HTTP; the client resubmits) |

Sources:

- Error classification:
  - main: `rpc.rs` `acl_err`, which maps every ACL call error to a network error.
  - v0.13.8: `decryption.rs:98-102, 200-209, 233`, which maps it to `ProcessingError::Recoverable`.
- Attempt limit: `max_decryption_attempts`, set to 3 in the harness.
- main's call timeout: `connect_to_rpc_node_with_bounds` (`crates/utils/src/conn.rs`, called from `KmsWorker::from_config`), at `Config::default().host_rpc_call_timeout` = 10 s.
- v0.13.8: `connect_to_rpc_node`, a plain HTTP client with no timeout.

The TC13 worker gets the same provider that production builds (decision D1).

`decryptionSignatureInvalidatedBefore` (main only) is Zama's signature-freshness getter, not an authorization view.
Its 88 cells are recorded for information. Every failure of that call also fails the request closed.

## Method

- **Harness.** Each request runs through a fresh, unmodified kms-worker against the Level 0 ACL on a local anvil (127.0.0.1, random mnemonic). The worker gets neutral gateway and KMS mocks, as in Phase 3 Level 0. The connector source is identical to the pristine clone in every run: `diff -rq` reports IDENTICAL, and the tree hashes of `crates/kms-worker/src` and `crates/utils/src` are EQUAL. See each run's `provenance.txt`.
- **Fault proxy.** `impl/harness/phase4/fault_proxy.py` sits between the worker and anvil. The worker's host-chain URL for a request is `<proxy>/tc13.<run>.<path>.<subject>.<view>.<fault>`. The proxy injects `<fault>` into every `eth_call` whose selector is `<view>`'s and passes every other call through. Its record (`host_rpc.jsonl`) shows each injection; every faulted cell fired in every run (the matrix's "Fault fired" column).
- **Subjects.** Allowed subjects are U (a legacy anvil account), Uk (an RFC-016 local key) and delegator U. Retired subjects are R (anvil account 4) and Rk (a local key). These are granted and delegated like U and Uk, then retired with `retireAccount()`. The real answer for a retired subject is therefore `false`.
- **Cases.**
  - main: 9 (path, view) cases. These are the legacy direct and delegated paths, RFC-016 direct and delegated, and RFC-016 direct over HTTP, crossed with each authorization view and `decryptionSignatureInvalidatedBefore`.
  - v0.13.8: 2 cases, legacy direct and delegated. Its connector checks no signature and calls no other view (`decryption.rs`).
- **Verdict.** Outcome per request comes from the connector database:
  - forwarded: a response row; the KMS mock saw UserDecrypt and GetUserDecryptionResult;
  - refused: the request row is `failed`, or there is an error response for HTTP.
- **V1 rule.**
  - A refusal always conforms; V1 is a safety rule (decision D4).
  - A forward conforms only if the `true` it rests on was correct: control, `intermittent` after the retry, or `delay` with no timeout.
- **Availability note.** An allowed subject refused although a correct `true` was obtainable is flagged as an availability note, not a V1 failure. There is one such cell: RFC-016 over HTTP under `intermittent`. The endpoint answers `upstream_transient` and leaves the retry to the client.

## Permit-recipient question: not applicable on Zama

Neither line's request names a recipient other than its signer:

- **v0.13.8.** `gateway-contracts/contracts/Decryption.sol:160-162` signs `UserDecryptRequestVerification(bytes publicKey, address[] contractAddresses, uint256 startTimestamp, uint256 durationDays, bytes extraData)`. `:173-175` adds `delegatorAddress` for the delegated form. `IDecryption.sol:39-44` defines `DelegationAccounts {delegatorAddress, delegateAddress}`.
- **main.** `Decryption.sol:171-173` and `:187-189` define the same typed data. `IDecryption.sol:65-78` defines `UserDecryptionRequestPayload {userAddress, publicKey, allowedContracts, requestValidity, extraData, signature}`. Requests enter at `IDecryption.sol:399, 424, 450` on main and `:306, 326` on v0.13.8.

`publicKey` is the transport key that the shares are encrypted to. It is not an account, so no view can be
evaluated for it. V1's subjects on Zama are the user (or delegate), the delegator, and the contract. TC6 (the
permit role) moves to the Fhenix port (P2.1, decision D5).

## What this means for the ERC

- The claim in Backwards Compatibility, that verifiers which already read the gated views inherit Core unchanged, is now [M] on both lines. It covers errors, timeouts, reverts and empty or truncated answers.
- It is stated with one condition: V1 counts every malformed answer as false. A verifier must therefore decode a view answer strictly. Anything that is not exactly one ABI-encoded `bool` (32 bytes, value 0 or 1) is false.
- The ERC now says this in V1 itself, and Backwards Compatibility makes the claim conditional on it.

## Harness notes

- **HTTP rows marked "runs differ."** In some runs, the Level 0 harness read an HTTP request's outcome before the error row was written, so no error code was recorded ("attempts 0"). This is the race fixed in the Level 1 harness (Phase 3). The outcome (refused, no KMS hit) is the same in every run.
- **Run time.** About 3.5 min per v0.13.8 run (52 requests) and about 14 min per main run (234 requests).
