# Level 1, part 2: Profile H in the connector (kms-worker at main)

**Status.** The connector part of Level 1 is done for the prototype. The main kms-worker now runs the Profile H crate
(part 1, `PROFILE_H_CRATE.md`) and adds three rules:
- **H5 / V7, final retirement denials.**
- **H6, refusal of regular-code users on the ECDSA-only legacy path.**
- **The code-first signature check** (H2, H8) on the RFC-016 path.

**Off by default.** With `profile_h.enabled = false` the connector is unchanged: the same code path and zero new RPC
(section 4).

**The real-chain run: 4/4 tests, 27/27 requests as expected.** It ran on the VPS with the Level 0 ACL v0.8.0 on anvil,
and the coordinator's analysis of the wire found no problem. Highlights:
- **The lapse run** is the case V7 exists for. A retired user's request was denied once. A simulated governance lapse
  then cleared the retirement bit.
  - With Profile H off, the queued retry **forwarded the request to the KMS**: the lapse revived it.
  - With Profile H on, the first denial was final, and the lapse revived nothing.
- **A 7702 account whose delegate refuses every signature** is forwarded today through its root key. Under `enforce`
  it is refused before the KMS. `shadow` forwards it and logs the would-be rejection.
- **H6.** A user with regular code is forwarded on the legacy path today and refused under H6. A 7702 delegate stays
  accepted.

**H5 rule as implemented.** After a check denies, the connector asks `isAccountRetired` for that check's subjects, in
order. If one answers true, the denial becomes `Irrecoverable` with `ErrorCode::AccountRetired`.
- Legacy direct: user, then contract.
- Legacy delegated: delegator, delegate, contract.
- RFC-016 direct: user.
- RFC-016 delegated: owner, user, contract.
- `allowedContracts`: final only when every listed contract is retired (any-of semantics).

The extra calls come only after a denial, so an allowed request pays nothing.

**Why "final" is sound.**
- Retirement is one-way (R2), so a check that rests on a retired account can never pass again.
- That includes E1: a successor can no longer be confirmed after retirement.

## 3. What this proves, and what it does not

**Proven [M]:**
- **V7 / H5 works in the connector.**
  - A denial that rests on a retired account is final at its first attempt on every path tested (legacy direct and
    delegated, RFC-016 on-chain and over HTTP) and is typed `account_retired`.
  - A governance lapse after that denial cannot revive the request. Without it, the lapse did revive it.
  - Ordinary denials keep today's retry behaviour.
- **H6 works on the legacy path.** It closes the "EIP-8298-migrated account still authorizes by its old key"
  case.
- **H2 / H8 in the connector.**
  - The B5 hole (a 7702 account's root key overriding its own delegate) is open today and closed under `enforce`.
  - `shadow` logs the would-be rejections without changing the outcome.
  - EOAs are unaffected.

**Not shown here:**
- The ML-DSA-44 budget through the connector. That is proven at the crate level (`PROFILE_H_CRATE.md` §5); the
  connector passes the same policy.
- H7 (re-checking stored results, dedup keyed on signature and validity window).
- H9 in the relayer and the SDK. That is part 3, `H9_PRECHECKS.md`.
- A restart. The H4 attempt state is in memory: a restart forgets it, which can grant at most two more ERC-1271
  attempts to a request already being retried.

**Observation (H4 under no block progress).**
- Anvil mined no block between attempts, so after the first negative every later attempt was `AwaitingNextBlock`.
  That attempt makes no call, but the connector still counts it toward `max_decryption_attempts`.
- On a live chain, blocks advance every few seconds and the second negative comes one block later. Either way the
  request ends refused, and the number of `isValidSignature` calls stays at most 2.
