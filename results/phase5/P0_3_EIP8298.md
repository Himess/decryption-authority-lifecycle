# P0.3: EIP-8298 next to EIP-7851 (proof classes: Connector and Mock)

Date: 2026-10-22. Connector runs: VPS, three per tree. Mock runs: M1, three of the local verifiers and the SDK
precheck, three of the SDK's `getAuthorityStatus`.

## Background (read 2026-10-22; all drafts)

The texts are kept in `raw/eips/`, each checked byte for byte against its commit in `ethereum/EIPs`.

- **EIP-8298, "SETCODEFROM Code Reuse Instruction"** (Draft, created 2026-06-11). Read at `f4a9f965`
  (2026-10-22T18:43Z), and at `fa391567` (2026-10-12) before it.
  - **The instruction.** `SETCODEFROM(source)` (opcode `0xA7`) sets the current account's code hash to that of a live
    account with regular deployed code (not empty, not starting with `0xEF`, not created in the same transaction).
  - **How an EOA uses it.** An EOA reaches it only by running EIP-7702 delegated code. Migration code stores the
    wallet's state (for example a post-quantum public key), then adopts a deployed wallet's code.
  - **After the adoption:**
    - the account has regular code, so its ECDSA-signed transactions are invalid under EIP-3607;
    - EIP-7702 cannot redelegate it, and no instruction returns it to empty code;
    - it acts through the adopted code, as the sender of EIP-8141 frame transactions its code approves, or when called.
    - The EIP's words: "This retires the account's key, not the account".
  - **Contracts that call `ecRecover`** still recover the address. EIP-8151 is named as the companion fix: empty
    output, as for a failed recovery, in the `f4a9f965` text. `fa391567` said "32 zero bytes", while EIP-8151's own
    text has always returned empty output.
  - **New at `f4a9f965`: two security notes.**
    - Code that offers no relay path of its own, on a chain without EIP-8141, is stranded.
    - An adoption authorized in advance should name the expected code hash, not only the source address.
- **EIP-7851** (Draft, at `07f3bb36`, unchanged since Phase 4: the same SHA-256 as `results/phase4/ENV.md`). An
  EIP-7702 account disables its ECDSA key. Its code becomes `0xef0101 ‖ delegate`.
- **EIP-8151** (Draft, at `e2fad38c`, 2026-10-18). `ecrecover` returns empty output for an account whose raw code is
  neither empty nor an EIP-7702 delegation indicator.

**Next to EIP-7851.** Both drafts end the key's authority on the host chain. Neither reaches an off-chain verifier
that recovers the signature in its own code. The two differ in what a verifier reads:

| | EIP-7851 | EIP-8298 |
|---|---|---|
| Code | `0xef0101 ‖ delegate`: 23 bytes, still a pointer to the delegate | the template's regular code (here 1,218 bytes); the account's own storage holds its state |
| Can a verifier tell it from a contract by its code? | yes (the `0xef0101` prefix) | **no**: it reads like any contract's code |
| Afterwards | the key stays disabled; code can switch the delegate (`SETSELFDELEGATE`, always to `0xef0101`) | the key stays retired; the adopted code can adopt other code |
| Profile H (H2) | regular code: ERC-1271 only, no fallback | the same |

## What is simulated, exactly

- **Simulated:** the account's state after the adoption.
  - X is a fresh local key.
  - Its code is set with `anvil_setCode` to the runtime code of a deployed `MLDSA44Account1271` (E4's ML-DSA-44
    ERC-1271 wallet, behind the Fireblocks verifier `cca262b5`, unaudited), and read back from the node.
  - The wallet keeps its state in immutables (the verifier, the key-blob address, the key hash), so its code is the
    whole wallet. There is no storage to copy, and `anvil_setStorageAt` is not needed here.
  - B3(b) repeats the simulation with the storage-based B0 wallet, setting its storage too.
- **Not simulated:**
  - the instruction itself, and the delegated migration code that would run it;
  - EIP-3607's refusal of X's ECDSA transactions (anvil does not apply it);
  - EIP-7702 redelegation being disabled;
  - block-level access lists, mempool rules, EIP-8141 frame transactions, and EIP-8151's precompile.
- **X's retirement** is sent through `anvil_impersonateAccount`, standing in for a call through its code. This wallet
  has no `execute`, so under EIP-8298 it would have no way to call `retireAccount()`: the "stranded" case of
  `f4a9f965`. B0's wallet adds an `execute` authorized by its ML-DSA-44 key.
- **Nothing rewrites what a verifier reads.** The JSON-RPC proxy runs with an empty rewrite table and only records
  the wire: 0 rewritten answers in the 9 connector runs and in the 6 local runs.
- **Y** holds NoErc1271's runtime (14 bytes, no `isValidSignature`): regular code that cannot answer ERC-1271.

**v0.13.8 [M].** The connector checks no user signature on this line; the gateway checks ECDSA only
(`Decryption.sol:923`). X, an anvil account holding NoErc1271's runtime, is forwarded on the legacy direct path and
on the delegated path (D for X, granted before the adoption). Once X is retired, both are refused. No `eth_getCode`
is made. Three runs, 4/4 rows each.

**What the wire shows beyond the outcome:**
- **The retired rows.** On the retired Level 1 rows, the worker reads the retirement view and the account's code
  concurrently, and drops the reads still in flight once it refuses. So the record differs between runs: no code read
  (r1); a code read sent and its answer not read (r2); a code read of 1,218 bytes (r3). The outcome is the same in
  all three.
- **The adopted code.** It is 1,218 bytes in every run. Its hash differs per run and tree (six hashes), because each
  run deploys the stack with fresh helper and key-blob addresses, which the immutables carry. NoErc1271's runtime has
  the same hash everywhere.
- **Provenance.** The `main` and `v0.13.8` harness trees have `kms-worker/src` and `utils/src` byte-equal to
  pristine. The Level 1 tree is `lifecycle/level1`, as built for Phase 4's P0.3 and P0.4.

## Specification changes

- **ERC.**
  - Motivation item 4 names EIP-8298 next to EIP-7851, "in simulations of both".
  - The Rationale paragraph is now "Relation to EIP-7851, EIP-8298 and EIP-8151". It adds migrating in place by
    adopting the wallet's code, and one sentence: an account that migrates in place can act, and so retire, only
    through its code.
- **EVIDENCE entry 9.** It adds the EIP-8298 simulation, its method, the date and this report.
- **Companion.**
  - A new term, **adopted code**.
  - "Regular code" includes adopted code, and so does H2.
  - Q4 and Q7: an account with adopted code is migrated.
  - **Q5, new clause.** A delegator whose code is regular now but was empty or a delegation indicator at B_Q adopted
    it after B_Q, and its changes before the adoption are cut off. Reading today's code cannot tell adopted code from
    a contract's, so the verifier reads the code at B_Q. A verifier without the host chain's state at B_Q cuts off
    every change of a regular-code delegator.
  - The relation section: EIP-8298, both EIPs' notes on `ecRecover`, and a SHOULD: a post-quantum wallet for this path
    exposes a call its post-quantum key authorizes and anyone can submit.
  - A new TC21 row (EIP-8298 part), and the evidence row.
- **Architecture, EN and TR.**
  - The recovery bullet of §4 gains the [M-P5] result.
  - §11.2 is now "EIP-7851 and EIP-8298", with an EIP-8298 bullet.
  - The residual table names both.
- **Write-up §5,** now "The host-chain gap: EIP-7851 and EIP-8298". It covers both simulations and the condition for
  migrating in place (a call path).
- **Other files.** The related-work line; the one-pager row; the README row; the split mapping; RESULTS §9.1.

**Q5 for adopted code is [Design] until measured.** The Level 3 worker's Q5 reads today's code and does not cut off
a regular-code delegator. The B_Q read is implemented and tested in B4 (DECISIONS_LOG D92).

Unchanged on purpose:
- `docs/FHE_Yetkilendirme_PQ_Tasarim.md` (the early design note) and the archives;
- the Phase 4 EIP status table in the architecture documents, which is a reported claim [C] from 2026-10-21. No
  statement is made here about which EIPs a fork will include.
